# Использование ИИ при разработке

Проект разрабатывался с помощью Claude (Anthropic) в качестве AI-ассистента.
Ниже — укрупнённый план (prompt), по которому велась разработка. Архитектурные
решения, финальный код и его качество — ответственность автора; сгенерированные
части кода прошли ревью и были адаптированы под требования задания.

## Использованный план (сокращённо)

1. Спроектировать план решения тестового задания «Авито.Кухня»: CJM клиента и
   заведения, C4-архитектуру (context/container/component), схему PostgreSQL,
   REST API (Client API + Venue API), Docker Compose инфраструктуру.
2. Сгенерировать скелет монорепозитория на Go:
   - `core` — основной сервис (chi-роутер, слоистая архитектура
     domain/usecase/transport/repository, pgx-репозитории, транзакционное
     создание заказа с блокировкой строк меню);
   - `restaurant-service` — сервис-пример заведения (клиент к Venue API,
     эмулятор кухни, приём webhook + fallback-поллинг);
   - миграции PostgreSQL (схема + dev-сиды);
   - OpenAPI-спецификации Client/Venue API;
   - PlantUML-диаграммы CJM и C4;
   - Docker Compose, Makefile, конфигурация golangci-lint.
3. Проверить компилируемость (сборка модулей), устранить несостыковки типов и
   пакетов, выявленные при генерации кода.

## Что было проверено вручную

- Корректность бизнес-правил конечного автомата статусов заказа
  (`domain.CanTransition`) — покрыто тестами.
- Логика транзакционного создания заказа с `SELECT ... FOR UPDATE` на позициях
  меню — защита от гонки между проверкой наличия и списанием.
- Соответствие структуры репозитория и слоёв заявленной в плане архитектуре.
- Реальная сборка (`go build ./...`), статический анализ (`go vet ./...`) и
  юнит-тесты (`go test ./... -race -cover`) для обоих модулей — прогнаны и
  зелёные; по ходу найден и исправлен цикл импорта в транспортном слое.
